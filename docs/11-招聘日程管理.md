# 招聘日程管理

## 使用方式

导航进入「招聘日程」，按公司、岗位或考点搜索，查看未取消、已取消或全部日程。每场活动显示时间、开始／截止含义、参加方式、考点、地址、考场、活动编号、轮次、版本和邮件变更历史。未知地点显示待通知，不根据公司地址猜测。

每场日程的「调整」入口可人工更正或清空错误地点、改期、取消和恢复。人工调整也保存历史版本并同步本场自动提醒；更改或清空时间须明确选择改期。

邮件分析沿用 IMAP 增量读取和去重。正文与已附带的 PDF、DOCX、Excel、文本和日历附件参与提取；没有投递回执也可以建立申请及首场日程。首次邀请缺少活动时间时保留待复核。

「邮件分析 → 应用到追踪」可修正提取信息，选择申请、原日程和操作。选原日程会带出所属公司、申请及类型。「新场次」不会覆盖既有活动；改期、取消和补充必须找到已有场次。需要复核的结果不会靠模型置信度强行落库。

| 邮件内容 | 日程行为 | 提醒行为 |
| --- | --- | --- |
| 首次考试／面试邀请 | 创建场次，同一活动重复通知保留为来源 | 未来活动及提前 24 小时准备提醒 |
| 附件、准考证、预约成功补充考点／考场 | 更新已关联场次，保留原时间 | 更新本场提醒中的地点 |
| 明确改期，新时间已知 | 保存新时间及历史版本 | 移除旧的未完成自动提醒，按新时间重建 |
| 延期，新时间另行通知 | 标为「延期 · 等待新时间」 | 撤销旧的未完成自动提醒 |
| 明确取消 | 标记已取消，不等于申请被拒 | 撤销本场未完成自动提醒 |
| 明确恢复，时间确定 | 恢复为已安排 | 按确认时间重建提醒 |
| 旧通知晚到／历史补扫 | 留档，不覆盖较新安排 | 保持当前提醒 |

保留已完成提醒和手工提醒；只替换带有本日程归属的未完成自动提醒。已有同申请、类型和时间的手工提醒不重复生成，也不擅自删除，用户应核对自己维护的事项。改期后不假设原预约窗口仍有效，准备事项由新通知重新确认。切换到线上时清除旧线下考点、地址及考场，不保存或打开考试链接。

## 跨邮件关联规则

### AI 面试、限时测评和重复催办

有效期内自行完成的活动使用 `timeKind: window`，同时保留完整开放时间和完成截止时间。即使开放时间仍在未来，也会创建截止提醒及截止前一天提醒；界面跨日显示完整日期，不把三天的作答窗口显示成同一分钟。

正文中带明确标签、完整起止日期且唯一的时间窗口，可补全模型遗漏的时间引文。多个不同窗口、模型与原文冲突仍需复核。“AI面试”“正式作答”属于参加形式，不用来制造轮次编号。

重复通知的岗位名称被简写时，须同时满足：同公司、同活动类型、同发件邮箱与主题、相同完整窗口（或与已确认窗口一致的截止时间）、岗位名称包含关系且至少四字符、唯一场次、无活动编号及轮次冲突，才关联原申请。明确职位编号优先隔离；缺编号时不会合并到带职位编号的另一申请。重复催办仅增加来源记录并维护同一套提醒，不重新按收件时间延长截止。截止时间变化需按改期确认。

若升级期间旧版进程确认了邮件却未生成日程，后续应用该公司的活动通知时会尝试接入：仅采用已确认、有有效时间、无复核问题、该申请及类型尚无日程且历史场次唯一的邀请。接入与本次通知应用共用事务，不会在失败后留下重复申请。升级完成后应重启后端，避免继续运行旧代码。

1. 先按公司及职位编号／唯一完整岗位确认申请。同公司不同职位不混合。
2. 在该申请及活动类型范围内，优先匹配活动编号；缺编号时使用原活动时间，或补充／取消通知中唯一匹配的明确轮次。
3. 多个匹配场次、岗位与活动编号冲突、原时间或轮次冲突、无法判断通知先后时保留待确认。只有一场活动也不会在完全缺乏依据时盲目关联。
4. 可人工指定场次，但仍须属于所选申请和类型，活动编号冲突不能强制覆盖。日程版本更新后须刷新重审，避免旧弹窗覆盖新通知。

活动编号不是职位编号、简历编号、身份证号、准考证号或候选人编号。公司别名、轮次不同写法不做模糊合并。取消后普通地点补充不会复活日程，必须明确恢复。

## 时间、来源及安全边界

投递回执按收件时间；考试／面试按正文或附件，转换成本机时间并另存原文时区说明。模型收到本机时区作为转换目标。多个地区／场次或有歧义时不能擅选。开始和登录截止独立标识；预约窗口、客服时间不能冒充考试起止。

变更、活动标识、地点和考场必须有可在正文／附件核对的引文。模型空响应仅增加输出预算重试一次，其他错误或重试仍失败则降级本地规则。通用规则保持低置信度供确认，不能保证所有邮件格式均可无人工识别。

只读邮箱，不发送邮件、不改变已读状态、不打开外部链接、不下载链接指向的准考证。认证邮件跳过，URL 和常见验证码脱敏；邮件里的指令不能控制程序。附件通过有超时和资源限制的独立进程读取文本，不运行宏或附件程序。扫描 PDF、图片 OCR、加密附件及超限文件仍需本人查看。预约、登录、身份核验、一次性考试入口、锁定考位或打印准考证均由本人操作。

来源与变更历史保存在本地数据库，不进入公开快照或代码仓库。当前是应用内待办提醒，需要打开应用查看，不提供关机后的系统推送。

## 升级及 API

数据库 v8 新增 `recruitment_schedules`、`schedule_sources`，提醒增加 `schedule_id`。历史已确认且有明确时间的考试／面试按申请、类型、时间接入；保留原邮件和时间线，仅采用能明确识别的旧邮件自动提醒。无法确认归属的历史提醒保持原样。

- `GET /api/email/schedules?applicationId=...`：日程、结构化字段及来源历史。
- `PATCH /api/email/schedules/:id`：人工调整，传 `revision`、`schedule`、`eventTime`、`eventTimeEnd`；版本不一致拒绝覆盖。
- 提取新增 `schedule`：`action`、`eventRef`、`round`、`previousTime`、`mode`、`venue`、`address`、`room`、`timezone`、`timeKind`、`evidence`。
- 邮件应用新增 `targetScheduleId`、`expectedScheduleRevision`：正整数选原场次，`null` 明确新场次，省略按证据匹配。
- 邮件确认、日程版本、提醒和申请状态处于同一事务，失败不会留下半条记录。

升级前使用 SQLite 在线 backup 备份，升级后重启后端并刷新页面。不要只复制正在写入的 `.db` 而忽略 WAL。

## 验证

```bash
pnpm check                 # 单测、类型、构建、API、PDF/DOCX/XLSX 附件
pnpm test:ui               # 原界面及日程完整流程，含暗色和手机布局
pnpm test:schedule:live    # 显式使用配置的 LLM，仅发送虚构邮件及附件文本
```

覆盖不同岗位、多轮活动、附件来源、地址补充、改期、取消、恢复、延期待定、重复应用、旧邮件晚到、手工提醒保护、版本冲突、跨公司误关联和旧数据库接入。真实模型测试使用两家虚构雇主的四类通知，不消耗真实考试链接；失败保留非零退出码。
